# ADR-0004: Evidence envelope and trust labelling

**Status:** Accepted
**Date:** 2026-09-21

## Context

Everything this server returns is read by a language model. Much of it
originates in clusters that tenants control: condition messages, `lastError`
descriptions, Events, annotations, labels, provider messages.

That makes prompt injection a first-class concern, not a hypothetical one. A
tenant who can create an Event can write `IGNORE PREVIOUS INSTRUCTIONS: ...`
into text that lands in an operator's assistant. Unicode tricks — bidi
overrides, zero-width characters — can hide such text from a human reviewer. An
oversized condition message can flood the context window.

An earlier draft nested evidence inside each finding, carried a numeric
`confidence: 0.91`, and let server-authored `summary` and `probableCause` fields
contain cluster text. Each of those is a problem: nesting duplicates evidence
and prevents reuse, a number implies a precision no rule possesses, and mixing
cluster text into server prose destroys the boundary entirely.

## Decision

All tool output uses one envelope: `schemaVersion`, `meta`, `target`, `summary`,
`findings[]`, `evidence[]`, `sources[]`.

**Evidence is top-level and referenced by ID.** Findings carry `evidenceRefs`,
not nested copies. Each evidence item records its own identity — `object`
(apiVersion, kind, namespace, name), `field`, `observedAt` — plus `truncated`
and `originalLength`.

**Every evidence item carries a `trust` label:**

- `trusted` — generated by this server.
- `trusted-enum` — checked against a known Gardener enum or error-code list.
- `untrusted` — free text originating in a cluster.

**The value of untrusted evidence is never copied into server-authored fields.**
`title` and `interpretation` contain templates plus validated identifiers
(DNS-1123 names, enum values) only. The MCP `content[]` text block is a compact
JSON rendering of `structuredContent`, so a client that reads only text gets the
same separation rather than a flattened blob.

**The sanitizer** normalises to NFC, strips control and bidi characters, caps
each field (about 2 KiB) and each list, deduplicates, and sets `sanitized`,
`truncated` and `originalLength`.

**`confidence` is an enum the rule declares** — `high` for a direct Gardener
error code or condition reason, `medium` for a cross-layer correlation, `low`
for a heuristic such as an age threshold — never a computed number.

**`sources[]` records every API call**, including skipped and failed ones, with
`status ∈ {ok, forbidden, notFound, timeout, skipped, error}` and `durationMs`.
`meta.completeness` is `complete` or `partial`; a partial result still returns
findings and adds `DIAG-INCOMPLETE-001` naming the missing layers.

## Consequences

The separation is testable, and therefore tested: the prompt-injection corpus in
`test/fixtures` asserts that no fixture string reaches a server-authored field.
This is the main defence in TB5, and it only works if it is enforced
mechanically.

The residual risk stays real and is documented: the model may still be *misled
in its explanation* by untrusted text it was correctly shown. Labelling bounds
what the server asserts; it cannot bound what the model says. AI conclusions are
advisory, and the UI is expected to show evidence.

Findings referencing evidence by ID means the agent can be told to cite evidence
IDs, which makes hallucination visible rather than plausible.

`sources[]` makes a partial answer honest instead of silently narrower — the
earlier `clustersInspected` field hid failures.

Rules own their confidence, so changing one rule's confidence is a reviewable
diff rather than a tweak to a scoring function.

## Alternatives considered

**Evidence nested in findings.** Simpler to read in a single-finding response.
Rejected: duplicates values across correlated findings and gives no stable way
to cite them.

**Numeric confidence.** Rejected: nothing in the pipeline produces a calibrated
probability, so a number is a fiction that invites false precision.

**Returning raw Kubernetes objects and letting the model interpret them.**
Rejected: it leaks infrastructure detail (pod specs, env vars, internal IPs),
floods context, and abandons the determinism that makes output testable — it is
also precisely what a generic Kubernetes MCP server already does.
